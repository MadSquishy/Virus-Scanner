Structure/Practices:
CMakeLists.txt holds the directions, typically one in each module so that things can be internally run, i.e for automated testing
0 there may be higher level global CMakeLists which will dictate how the different modules interact.

COMMANDS:
set
0 sets variables and their values, good for managing flag variables
0 ex: set(CMAKE_CXX_STANDARD 20)

add_executable 
0 is how makefile targets are made.
0 however, this will only work if x and y are in the same directories so that x can include y.hpp
0 if multiple files are given, it will also handle linking
0 ex: add_executable(x x.cpp y.cpp)

add_subdirectory
0 calls the given subdirectory's cmakelists as part of the current running cmakelists. 
0 the lower subdirectory keeps the flags and everything else that comes with the scopes of the higher level one which is being called. 
0 ex: add_subdirectory(dirname)

add_library
0 stores the given directory, and what is in it, so it can be used for linking later, effectively creates libraries you can link using the next function
0 ex: add_library(parser_lib parser.cpp parser.hpp)
0 this would be written in parser/CMakeLists.txt and called from the source file with add_subdirectory

target_link_libraries
0 explicitly says what to link at link time, often used in conjunction with executable, library (duh) and subdir
0 uses PRIVATE and PUBLIC flags to manage dependancy chains

0==0 
0 ex: target_link_libraries(app PRIVATE/PUBLIC parser_lib)
